# APIpilot — Apple-Inspired Design Skill

## 1. Purpose

You are the UI/UX design authority for **APIpilot**.

Your job is to make APIpilot feel like a **real, premium developer product designed by an experienced product designer**, not an AI-generated SaaS template.

The design direction is:

> **Apple-inspired restraint + modern developer tooling + APIpilot's own identity**

Do not copy Apple's visual assets, layouts, branding, or proprietary design. Use the underlying principles of clarity, hierarchy, whitespace, typography, consistency, and intentional interaction design.

---

# 2. Core Design Philosophy

APIpilot should feel:

- Premium
- Calm
- Precise
- Intelligent
- Technical
- Simple
- Trustworthy
- Human-designed
- Intentional

APIpilot should NOT feel:

- Generic AI SaaS
- Over-designed
- Cyberpunk
- Template-driven
- Visually noisy
- Excessively futuristic
- Filled with unnecessary cards
- Covered in gradients
- Covered in glassmorphism
- Overly rounded
- Obviously generated by an AI UI generator

Every visual decision must have a reason.

---

# 3. Primary Design Principle

## Simplicity is not emptiness.

Do not remove useful information simply to make the interface minimal.

Instead:

1. Identify the user's primary task.
2. Give that task visual priority.
3. Hide secondary complexity through progressive disclosure.
4. Use whitespace to establish hierarchy.
5. Remove decoration that does not improve comprehension.

The interface should feel simple because the **information architecture is good**, not because information has been removed.

---

# 4. Anti-AI Design Rules

Before implementing or redesigning a page, actively check for these common AI-generated patterns.

### Avoid

- Purple-to-blue gradients
- Neon gradients
- Glowing borders
- Excessive backdrop blur
- Glassmorphism everywhere
- Huge rounded containers
- `rounded-2xl` / `rounded-3xl` on every component
- Excessive drop shadows
- Every section being a card
- Identical cards repeated across the page
- Giant meaningless hero sections
- Random decorative blobs
- Floating gradient circles
- Excessive icons
- Emoji as UI decoration
- AI sparkles everywhere
- "Powered by AI" badges everywhere
- Excessive animations
- Large empty areas with no hierarchy
- Generic dashboard layouts
- Arbitrary colors
- Multiple competing accent colors

### Prefer

- Typography
- Whitespace
- Subtle borders
- Strong hierarchy
- Restrained color
- Clear grouping
- Consistent spacing
- Purposeful motion
- Meaningful icons
- Content-driven layouts
- Progressive disclosure
- Contextual AI interaction

# 5. Visual Identity

APIpilot should have a neutral visual foundation.

### Light mode

Primary background:

`#FFFFFF`

Secondary background:

`#F5F5F7`

Tertiary background:

`#FAFAFA`

Primary text:

`#1D1D1F`

Secondary text:

`#6E6E73`

Borders:

`#E5E5E7`

The accent color should be restrained and used primarily for:

- Primary actions
- Active states
- Links
- Focus states
- Important system feedback

Do not use the accent color as decoration.

---

# 6. Dark Mode

Dark mode should not simply invert the light theme.

Use carefully layered dark surfaces.

Suggested foundation:

```text
Background:      #0B0B0D
Surface:          #141416
Elevated Surface: #1C1C1F
Primary Text:     #F5F5F7
Secondary Text:   #A1A1A6
Border:           #2C2C2E
```

Avoid pure black backgrounds unless there is a strong reason.

Avoid neon/glowing dark-mode aesthetics.

---

# 7. Typography

Typography is one of the most important parts of the APIpilot identity.

Prefer a modern sans-serif system similar in character to:

- SF Pro
- Inter
- Geist

Use a monospace font only where it improves comprehension:

- API endpoints
- HTTP methods
- Request bodies
- Response bodies
- JSON
- Headers
- Logs
- Code
- IDs

Do NOT use monospace typography throughout the application.

---

# 8. Typography Hierarchy

Use a strong hierarchy.

Example:

```text
Page title
32–48px

Section title
22–28px

Subsection
16–20px

Body
14–16px

Secondary information
13–14px

Metadata
12–13px

Code
13–14px
```

Avoid making every heading huge.

Large typography should communicate importance.

---

# 9. Spacing System

Use a consistent spacing rhythm.

Prefer multiples of:

```text
4
8
12
16
24
32
48
64
80
96
```

Avoid arbitrary spacing values unless necessary.

Use more whitespace around major sections and tighter spacing inside functional groups.

Example:

```text
Page
  ↓ 48px

Section
  ↓ 24px

Component
  ↓ 16px

Related controls
  ↓ 8px

Individual elements
```

---

# 10. Border Radius

Use restrained radius values.

Recommended:

```text
Small controls: 6px
Inputs:         8px
Buttons:        8px
Cards:          10–12px
Large surfaces: 12–16px
```

Do not automatically use large pill shapes.

Pills should be reserved for:

- Tags
- Status indicators
- Filters
- Compact controls

---

# 11. Shadows

Prefer borders over shadows.

Use shadows only when establishing elevation is necessary.

Hierarchy:

```text
No shadow
↓
Subtle shadow
↓
Medium shadow
```

Never use dramatic shadows to make ordinary components look "premium."

Premium should come from:

- typography
- spacing
- hierarchy
- materials
- interaction quality

---

# 12. Buttons

Buttons should feel functional and confident.

Primary button:

- Strong contrast
- Simple shape
- Clear label
- Minimal decoration

Secondary button:

- Neutral background
- Subtle border

Tertiary action:

- Text or icon button

Avoid:

- Gradient buttons
- Glow buttons
- Excessively rounded buttons
- Decorative icons inside every button

Use icons only when they improve recognition.

---

# 13. Cards

Cards should NOT be the default solution for organizing content.

Before creating a card, ask:

> Does this information actually need a separate surface?

Prefer:

- sections
- dividers
- whitespace
- columns
- grouped controls

Use cards when they communicate a meaningful boundary.

Examples where cards make sense:

- Saved API project
- AI suggestion
- Environment configuration
- Important system state
- Independent resource

Do not put every statistic inside a separate card.

---

# 14. Navigation

Navigation should be quiet and predictable.

Avoid oversized dashboards.

Primary navigation should make it immediately obvious:

- Where am I?
- What can I do?
- What is the primary action?
- What is secondary?

Use visual emphasis sparingly.

The active navigation item should be obvious without becoming visually dominant.

---

# 15. API Workspace

The API workspace is the heart of APIpilot.

It should feel more like a **professional developer tool** than a marketing page.

Prioritize:

```text
Request
↓
Configuration
↓
Execution
↓
Response
↓
AI assistance
```

A possible structure:

```text
┌─────────────────────────────────────────────┐
│ Workspace / Collection / Environment        │
├──────────────┬──────────────────────────────┤
│              │                              │
│ Collections  │ Request                      │
│              │                              │
│ Endpoints    │ GET /users                   │
│              │                              │
│              │ Headers  Params  Body        │
│              │                              │
│              │ [ Send Request ]             │
│              │                              │
├──────────────┴──────────────────────────────┤
│ Response                                     │
│                                             │
│ 200 OK                                      │
│ JSON                                        │
└─────────────────────────────────────────────┘
```

The workspace should optimize for **focus and speed**.

---

# 16. AI Experience

AI should be a **capability**, not the visual identity of the entire application.

Do not put AI branding everywhere.

Instead, AI should appear when it can help.

Examples:

```text
Generate request
Explain response
Generate tests
Detect API issue
Suggest headers
Generate documentation
Explain error
```

The AI assistant should feel like:

> "A smart teammate available when needed."

Not:

> "A chatbot attached to every screen."

---

# 17. AI Interaction Pattern

Prefer contextual AI actions.

Example:

```text
Response

200 OK

[ JSON ] [ Headers ] [ Preview ]

        Explain this response
              ↑
       contextual AI action
```

Rather than:

```text
✨ AI MAGIC
✨ AI POWERED
✨ ASK AI
✨ AI ASSISTANT
✨ AI GENERATOR
```

everywhere.

When presenting APIpilot UI:

- Use realistic data

# 20. Empty States

Empty states should be useful, not decorative.

Bad:

```text
✨ Nothing here yet!
Let's get started 🚀
```

Prefer:

```text
No requests yet

Create your first request to start exploring this API.

[ Create request ]
```

Keep empty states concise.

---

# 21. Error States

Errors should be calm and informative.

Never make errors visually dramatic unless the severity requires it.

Show:

1. What happened
2. Why it happened if known
3. What the user can do next

Example:

```text
Request failed

401 Unauthorized

The API rejected your credentials.

[ Check authentication ]
```

---

# 22. Loading States

Avoid unnecessary spinners.

Prefer:

- skeletons for page-level loading
- subtle progress indicators for requests
- inline loading states for actions

Loading should preserve layout stability.

---

# 23. Motion

Motion should be subtle.

Use animation for:

- navigation transitions
- modal appearance
- expanding panels
- state changes
- request execution
- AI responses
- hover feedback

Avoid:

- excessive bouncing
- floating elements
- dramatic page transitions
- constant movement
- animation purely for decoration

Animation should communicate:

> **Where did this come from? Where is it going? What changed?**

---

# 24. Responsive Design

Do not simply shrink desktop layouts.

For smaller screens:

- simplify navigation
- prioritize primary actions
- collapse secondary information
- stack complex panels
- preserve readable typography
- maintain touch-friendly controls

The mobile experience should feel intentionally designed.

---

# 25. Component Consistency

Every component must belong to the same visual language.

Before creating a new component, check whether an existing component can be reused.

Maintain consistency across:

- buttons
- inputs
- dropdowns
- tabs
- modals
- cards
- tables
- badges
- navigation
- tooltips
- alerts
- AI components

Do not create five visually different button styles for five different pages.

---

# 26. Data-Dense Interfaces

Developer tools require information density.

Do not confuse Apple-inspired design with excessive whitespace everywhere.

The rule is:

> **Whitespace around information. Density within workflows.**

For example:

Marketing page:

```text
LOW DENSITY
Large typography
Large spacing
Few elements
```

API workspace:

```text
HIGHER DENSITY
Requests
Headers
Parameters
Response
Logs
Controls
```

Both can still feel like the same product.

---

# 27. Design Before Code

When asked to redesign a page:

### Step 1 — Inspect

Understand:

- current layout
- existing components
- information architecture
- user flow
- visual hierarchy
- responsive behavior

### Step 2 — Critique

Identify:

- AI-generated patterns
- unnecessary components
- visual noise
- inconsistent spacing
- weak hierarchy
- poor interaction patterns

### Step 3 — Establish direction

Decide:

- layout
- hierarchy
- typography
- spacing
- color usage
- component structure

### Step 4 — Implement

Only then modify the UI.

### Step 5 — Review

After implementation, inspect the result as a senior product designer.

Ask:

- Does this feel generic?
- Is there too much decoration?
- Is the hierarchy obvious?
- Are there too many cards?
- Are the colors restrained?
- Is typography doing enough work?
- Does the interface feel coherent?
- Does it look like a real product?
- Is the primary user task obvious?

### Step 6 — Refine

Make targeted improvements.

Do NOT redesign the entire interface again simply because it could look different.

---

# 28. Human Design Test

Before considering a page finished, ask:

> **Could this exact interface have been generated from a generic SaaS prompt?**

If the answer is yes:

- remove generic decoration
- improve hierarchy
- introduce product-specific patterns
- improve content
- refine spacing
- make the layout more intentional

The goal is not to make APIpilot unusual for the sake of being unusual.

The goal is to make it **specific to APIpilot**.

# 30. Implementation Rules

When writing frontend code:

- Prefer reusable components.
- Reuse existing design tokens.
- Avoid one-off styling.
- Avoid arbitrary colors.
- Avoid arbitrary spacing.
- Avoid unnecessary dependencies.
- Preserve existing functionality.
- Do not change business logic while redesigning UI unless explicitly requested.
- Do not rewrite working components unnecessarily.
- Keep accessibility intact.
- Maintain keyboard navigation.
- Maintain responsive behavior.

If Tailwind is being used, favor semantic design tokens and reusable component classes rather than scattering arbitrary values throughout the application.

---

# 32. Golden Rule

When uncertain between two designs:

> **Choose the simpler one.**

When uncertain whether to add decoration:

> **Don't add it unless it improves comprehension or interaction.**

When uncertain whether something needs a card:

> **Try whitespace and hierarchy first.**

When uncertain whether to add an animation:

> **Only animate if it communicates a state or improves the interaction.**

When uncertain whether AI should be visible:

> **Make the AI useful before making it visible.**
